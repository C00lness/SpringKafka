# Безопасность в микросервисном проекте (Шпаргалка)

**Основной принцип:** Stateless-аутентификация (без хранения сессий на сервере).

### 1. Хранение паролей
*   **BCrypt:** Пароли никогда не хранятся в открытом виде. Используется `BCryptPasswordEncoder` для хеширования с солью.

### 2. Аутентификация (Кто ты?)
*   **JWT (JSON Web Token):** Клиент отправляет логин/пароль на `/auth/login`. Сервер проверяет их и генерирует подписанный токен (внутри `username` и время жизни).
*   **Секретный ключ:** Токен подписывается ключом (`jwt.secret`), чтобы его нельзя было подделать.

### 3. Авторизация (Что тебе можно?)
*   **JwtFilter:** Кастомный фильтр (наследник `OncePerRequestFilter`), который перехватывает каждый запрос.
*   **Проверка:** Фильтр достает токен из заголовка `Authorization: Bearer <token>`, проверяет подпись и срок действия.
*   **SecurityContext:** Если токен валиден, фильтр кладет объект аутентификации в `SecurityContextHolder` (Spring Security считает пользователя авторизованным).

### 4. Правила доступа
*   **SecurityFilterChain:**
    *   `/auth/**` и `/actuator/**` — открыты (`permitAll()`).
    *   Все остальные — требуют авторизации (`authenticated()`).
*   **CSRF:** Отключен (`.csrf.disable()`), так как нет куки-сессий.

### 5. Защита на уровне API Gateway
*   **Rate Limiting:** Ограничение количества запросов с одного IP (через Redis). Защита от DDoS и брутфорса. Спам отсекается до того, как долетит до микросервисов.

> *«В моем проекте безопасность была построена на stateless JWT: пароли хешировались BCrypt, при логине выдавался токен, а кастомный JwtFilter проверял его и устанавливал контекст Spring Security. На уровне Gateway работал Rate Limiting через Redis для защиты от спама. При этом я понимаю, что в корпоративном энтерпрайзе (как у вас) ручной JWT обычно заменяется на централизованный Identity Provider — Keycloak с OAuth 2.0 и OIDC. Я готов перестроиться на эту модель».*
