# Шпаргалка: Backend-разработка (заметки)

## 🚀 Redis
Сверхбыстрое хранилище в оперативной памяти. Используется для:
- увеличения счётчика;
- кеширования.

## 🗄️ HikariCP
Пул соединений с БД. Настраивается в `application.properties`.  
**Дефолтный размер пула — 10.**

### properties vs yaml
- `properties` — для маленьких проектов.
- `yaml` — для больших проектов со сложной иерархической структурой.

## 🔒 Блокировки БД
Нужны для пользования общими ресурсами.

### Пессимистичная vs оптимистичная
- **Пессимистичная** — транзакция сразу блокируется «на всякий случай».
- **Оптимистичная** — используем механизм версии: версия изменилась → повторяем.

## 📨 Kafka
- `enable.idempotence=true` — по умолчанию для продюсера в Kafka.
- **Частичные отказы** — обрабатываем через `try/catch`: в базу занесём, а Kafka — как получится.

## 🧩 Согласованность данных
- **2PC** — старый подход.
- **SAGA** — «модный молодёжный» подход с компенсирующими транзакциями (чтобы откатить уже созданное).

## 🔢 Версионирование
- версионирование данных;
- версионирование API.

## ⚠️ Обработка ошибок
`@RestControllerAdvice` — для обработки ошибок (используй со стандартными кодами ответов).

## 🔐 Безопасность
- **Keycloak** — сервер идентификации и управления доступом (используется вместо Spring Security).
- **OpenID Connect** — надстройка над OAuth 2.0 для аутентификации.
- **JWKS (JSON Web Key Set)** — публичный ключ, которым Keycloak подписывает токены.
- **ABAC / RBAC** — доступ по атрибутам / по ролям.

## 🧪 @Transactional
Вешаем на `@Service` (логика бизнеса). Либо на метод, либо на класс — в основном на класс.

### 3 грабли
1. Метод должен быть `public`.
2. Нельзя вызывать из того же класса (self-invocation).
3. Свалится, если будет checked-исключение.

# Тестирование в Java (Шпаргалка для собеседования)

---

## 🧱 1. Где писать бизнес-логику для тестов
*   **`@Service`** — вешаем на класс (реже на метод). Это слой бизнес-логики, который нужно покрывать тестами в первую очередь (расчеты, проверки, алгоритмы).

---

## 🧪 2. Виды тестов

### Unit-тесты (Модульные)
*   **Что проверяем:** Один конкретный метод (например, математическую формулу).
*   **Особенности:** Быстрые. Не требуют запуска Spring, БД или Kafka.
*   **Моки (Mockito):** Все внешние зависимости (репозитории, клиенты API) заменяются «заглушками» (моками). Мы проверяем только логику самого метода, изолируя его от инфраструктуры.

### Интеграционные тесты
*   **Что проверяем:** Как компоненты работают **вместе**. Например, что Hibernate реально сохраняет данные в PostgreSQL, или что Kafka-продюсер отправляет сообщение.
*   **Особенности:** Медленнее модульных. Требуют поднятия контекста Spring (аннотация `@SpringBootTest` или `@DataJpaTest`).

---

## 🐳 3. Testcontainers
*   **Что это:** Библиотека, которая поднимает **реальные** базы данных (PostgreSQL, MySQL) или брокеры (Kafka) в Docker прямо во время выполнения теста.
*   **Зачем нужен:** Лучше, чем использовать H2 (in-memory), потому что H2 может вести себя иначе, чем реальный PostgreSQL (разные диалекты SQL, другие ограничения). Testcontainers гарантирует, что тест пройдет так же, как в продакшене.

---

## 🎯 4. Параметризованный тест (`@ParameterizedTest`)
*   **Что это:** Позволяет прогнать один тест несколько раз с разными входными данными.
*   **Где использовать:** Идеально для проверки математических формул и расчетных алгоритмов (например, передаем 10 разных наборов длины и количества, и проверяем, что площадь считается верно).

---

## 📏 5. `delta` (погрешность)
*   **Проблема:** В тестах для чисел `double` или `float` нельзя писать `assertEquals(10.5, result)`, потому что компьютер может выдать `10.499999999` из-за особенностей хранения чисел с плавающей точкой.
*   **Решение:** Пишут `assertEquals(10.5, result, 0.001)`, где `0.001` — это допустимая погрешность (`delta`). Если разница между ожидаемым и реальным результатом меньше `delta`, тест считается пройденным.

---

## 🎓 Как ответить на собеседовании (одним абзацем)

> *«Для тестирования бизнес-логики (`@Service`) мы используем Unit-тесты с Mockito, изолируя код от БД через моки. Для проверки расчетных алгоритмов применяем `@ParameterizedTest` с таблицей контрольных примеров и обязательно указываем `delta` для чисел с плавающей точкой. А для проверки взаимодействия с инфраструктурой (БД, Kafka) используем интеграционные тесты на базе Testcontainers — это позволяет поднять реальный PostgreSQL в Docker и избежать расхождений, которые бывают при использовании in-memory H2».*
